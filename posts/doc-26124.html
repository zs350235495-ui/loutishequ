DOC-26124 防真实IP泄漏 2026-10-16 28 MINS

彻底封堵真实 IP 暴露：WebRTC、DNS 泄漏与 DoH/DoT 分流防劫持全链路排查指南

深入解析真实物理 IP 泄露根因：详析 WebRTC STUN 穿透、DNS 污染回落及全局代理 UDP 缺失三大协议漏洞，详解 DoH/DoT 与 Fake-IP 虚拟映射阻断机制，提供完整自查 Checklist、Mihomo/TUN 核心防漏规则与浏览器深度加固方案。

// SECURITY INCIDENT OBSERVATION // 安全工程事故归因

在网络攻防对抗与隐私安全领域，“真实物理 IP 暴露”往往是去匿名化（De-anonymization）分析的致命破口。许多运维人员、安全研究员及隐私关注者即便开启了代理工具的“全局代理”模式，在访问对抗级反欺诈或数字指纹检测平台时，其所属 ISP、地理经纬度乃至局域网内网拓扑依然在瞬间被精准捕获。传统基于操作系统 WinINet / HTTP 环境变量的代理机制，无法封堵原始 UDP 套接字与浏览器 P2P 穿透。

一、 真实 IP 暴露的三大核心协议漏洞底层剖析

1.1 WebRTC STUN 穿透机制：浏览器的“隐形后门”

WebRTC 为浏览器提供了无需任何插件即可进行低延迟音视频点播与 P2P 传输的能力。为了实现两台处于不同 NAT 之后的设备直接通信，WebRTC 实现了完整的 ICE（Interactive Connectivity Establishment，RFC 8445） 框架，底层深度绑定 STUN（RFC 8489） 与 TURN（RFC 8656） 协议。

  • 收集 ICE 候选者（Candidate Harvesting）：网页调用 RTCPeerConnection.createOffer() 时，底层 WebRTC 引擎立即触发候选发现。
  • 旁路 STUN 绑定请求：浏览器彻底绕过 WinINet/SOCKS 系统代理，直接通过系统默认路由向公网 STUN 服务器（如 stun.l.google.com:19302）发送原始 UDP 报文。
  • 反射地址回传：STUN 服务器返回 XOR-MAPPED-ADDRESS，包含用户真实出口公网 IP 与端口。
  • 内网网卡嗅探：同时收集 host 候选者（暴露 192.168.x.x 局域网私网 IP），页面 JS 异步捕获后回传，完成去匿名化。

1.2 本地 ISP 的 DNS 污染与 Fallback 回落机制

传统 DNS 运行在无连接、无加密的 UDP 53 端口上。本地 ISP 或骨干链路的 DPI 设备能够旁路监听所有查询，并在真实响应到达前注入 Bogon IP（如 0.0.0.0 或特定虚假 IP）。许多代理客户端为了追求快速解析开启了并发查询（Concurrent Query）或后备回落（Fallback）：由于本地 ISP 延迟极低（2-5ms），伪造报文抢答成功覆盖真实结果；或者当远程加密 DNS 超时时静默回落到本地运营商，导致用户访问的目标域名和真实 IP 彻底暴露在运营商日志中。

1.3 代理客户端“全局模式”下的 UDP 分流缺失

系统代理（System Proxy）本质仅在注册表写入 HTTP/HTTPS 代理端口，对底层 UDP 协议无任何拦截管辖权。当浏览器访问支持 HTTP/3 (QUIC) 的网站时，会优先发送 UDP 443 数据报文；此外游戏语音、STUN 穿透均基于 UDP。若 TUN 虚拟网卡未启用严苛路由（Strict Route），多网卡跃点竞争（Interface Metric Hazard）会使 UDP 流量直接逃逸到物理网卡。

二、 加密解析与阻断核心：DoH、DoT 与 Fake-IP 的安全拓扑

在传统的 Redir-Host 模式下，系统必须先向外部发起 DNS 解析获取真实目标 IP 才能发起连接，解析动作必须发生在“连接之前”，这使得 DNS 泄露不可避免。Fake-IP（虚拟保留 IP 映射）模式从架构时序上彻底逆转了这一流程：

[Fake-IP 运转时序]
1. 浏览器向 127.0.0.1 发送 A 记录查询: target.domain
2. 代理核心拦截请求，不向外网做任何查询，直接从 198.18.0.0/16 分配虚拟 IP (如 198.18.0.23)
3. 浏览器与 198.18.0.23 发起 TCP/UDP 握手，数据包被 TUN 虚拟网卡全量截获
4. 代理核心倒查哈希映射表还原真实域名，封装进 Shadowsocks/VLESS/Trojan 加密隧道发往远端
5. 真实 DNS 解析由境外远程节点代为完成，本地物理网卡零域名报文外发！

三、 全链路排障实操与加固配置

3.1 泄漏自查双重验证 Checklist

  • WebRTC 泄露检测：访问 browserleaks.com/webrtc，查看 Public IP 与 IPv6，出现本地真实运营商 IP 即为泄露。
  • DNS 泄露检测：访问 dnsleaktest.com 运行 Extended Test (6轮)，服务器归属地必须完全属于远程节点机房，不能有任何本地宽带。
  • 终端 Fake-IP 命中测试：dig +short twitter.com @127.0.0.1 -p 1053，必须返回 198.18.x.x。
  • 抓包验证 UDP 53 外溢：sudo tcpdump -i eth0 -nn -s0 "udp port 53"，访问境外网站时物理网卡应保持完全静默。

3.2 客户端核心分流配置示例 (Mihomo / TUN 加固)

tun:
  enable: true
  stack: mixed
  auto-route: true
  auto-detect-interface: true
  strict-route: true # 【必须开启】严苛路由阻断 Windows 多网卡侧信道泄露
  endpoint-independent-nat: true

dns:
  enable: true
  listen: 0.0.0.0:1053
  ipv6: false # 禁用 IPv6 阻断 Happy Eyeballs 侧信道直连
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.0/16
  fake-ip-filter:
    - "*.lan"
    - "*.local"
    - "+.msftconnecttest.com"

  default-nameserver:
    - 223.5.5.5
  nameserver:
    - https://223.5.5.5/dns-query

  # 策略分流：非国内域名全部交由远程代理节点加密解析，禁用明文 Fallback
  nameserver-policy:
    "geosite:geolocation-!cn":
      - "https://1.1.1.1/dns-query#PROXY"
      - "https://8.8.8.8/dns-query#PROXY"

rules:
  - DST-PORT,53,REJECT-DROP
  - DST-PORT,3478,REJECT   # 拦截 STUN 穿透端口
  - DST-PORT,19302,REJECT
  - AND,((DST-PORT,443),(NETWORK,UDP)),REJECT # 阻断 QUIC，强制降级为受控 TCP
  - GEOSITE,cn,DIRECT
  - GEOIP,cn,DIRECT
  - MATCH,PROXY

3.3 终端浏览器防 WebRTC 泄露策略加固

1. Chrome / Edge 策略锁定：注册表 HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome 下新建 DWORD WebRtcIPHandlingPolicy 设为 disable_non_proxied_udp，强制未走代理的 UDP 无法发起穿透。

2. Firefox 底层参数修改：地址栏输入 about:config，修改：
- media.peerconnection.enabled = false（完全关闭 WebRTC 堆栈，最安全）；
- 或保持开启并设定 media.peerconnection.ice.proxy_only = true 与 media.peerconnection.ice.no_host = true。

// CRITICAL PITFALL 01: 警惕本地 Fallback DNS 的并发毒化

许多用户在配置中随意填入 114.114.114.114 或运营商 DNS 作为后备。当网络轻微抖动触发超时重试时，本地 DNS 凭借超低物理延迟瞬间抢答被污染的结果，导致代理节点接收到 Bogon IP 建立连接失败。Fake-IP 体系下坚决不得配置任何不受信的本地明文 Fallback！

// CRITICAL PITFALL 02: 双栈 IPv6 导致明文绕行直连

现代操作系统遵循 RFC 6724 优先尝试 IPv6。若代理节点无原生 IPv6 出口或 TUN 网卡未完全接管 IPv6 默认路由，IPv4 会进入加密隧道而 IPv6 直接通过本地物理网卡直连泄露真实公网 IP。排障建议直接在 DNS 模块设置 ipv6: false 并在网卡属性中禁用 IPv6。

// ARCHITECTURAL VERDICT // 最终防御基线

彻底封堵真实 IP 暴露，必须构建“Fake-IP 本地虚拟映射 + TUN Strict-Route 物理阻断 + 浏览器 disable_non_proxied_udp 策略限制”的三位一体闭环防御。杜绝一切明文 UDP 53 外发，切断 STUN 旁路嗅探通道，方能实现真正不可逆向、零泄漏的高可信通信。
